# Security

## Reporting a vulnerability
Please **do not open public issues** for security vulnerabilities. Report them confidentially via
[GitHub Security Advisories](https://github.com/Coding9GmbH/coding9-lotse/security/advisories/new).
We acknowledge receipt within 3 business days.

## Security model (summary)
- **AI is read-only**: The language model only receives protected read clients with an allowlist (`ReadOnlyShopware` in `src/server/shopware.ts`, rules in `src/server/policy.ts`; per platform `reader.ts` under `src/server/platform/<platform>/`). Customer, order, invoice, payment, user and integration data are hard-blocked; sensitive fields are removed before hand-over; every access is recorded in the access log. Unused sample codes without a redeemer are included; customer data and who redeemed a code are not.
- **Writing only after approval**: Only the executor (`src/server/changes.ts`, platform-specific writers under `src/server/platform/`) writes. The approval is the marker `x-lotse: 1` plus `LOTSE_PASSWORD` if set – not a secret bound to the click. Throttled (`LOTSE_WRITE_CONCURRENCY`, default 2), with audit log and undo. Single proposals hold at most 300 rows. Batches (one rule for many products) go up to 10,000 (Shopware, Shopify) or 5,000 (Magento, OpenMage), imports up to 2,000 rows. The approval card shows the groups and a sample, not every row.
- **Shop protection**: Timeouts for every shop request (`LOTSE_SHOP_TIMEOUT_MS`), backoff on 429/503.
- **Credentials**: AES-256-GCM encrypted in the data volume; never passed to the AI and stripped from error messages. If a platform's shop address changes to a different origin (scheme, host, port), Lotse sets its stored secrets aside – they never go to a new host and must be entered again; they only apply again if the address points back to exactly the previous origin. Secrets from the environment only apply to the address from the environment.
- **Network**: Lotse is built for local operation (port bound to `127.0.0.1` only, host/origin check against DNS rebinding/CSRF; writing calls additionally require the UI's `x-lotse: 1` marker). For server operation, set `LOTSE_PASSWORD` and `ALLOWED_HOSTS` and put HTTPS in front with a reverse proxy (guide: [`docs/self-hosting.md`](docs/self-hosting.md), German). There is one shared password (UTF-8) and no user accounts. After 10 wrong passwords within 15 minutes Lotse blocks the source address for 5 minutes (429); access scope and further limits belong at the proxy. Loopback names (`localhost`) only count when the real socket address is local – a client-supplied `X-Forwarded-For` is not enough. `ALLOWED_HOSTS` without `LOTSE_PASSWORD` is reported at startup and in the settings. The UI and API send `X-Frame-Options: DENY` and a CSP with `frame-ancestors 'none'; object-src 'none'; base-uri 'self'; form-action 'self'` (no `script-src`, Next needs inline scripts).
- **Live preview** (`/shop`): Shop scripts run, but never in Lotse's origin: iframe `sandbox` without `allow-same-origin` and CSP `sandbox allow-scripts allow-forms` on the document (also when opened directly), `script-src 'self' 'unsafe-inline'` (no third-party scripts). No access to cookies, storage or the API; requests to Lotse fail the origin/marker check. All other proxy responses (images, SVG, XML, CSS, scripts) carry `sandbox; default-src 'none'` and `nosniff`: an SVG with a script from the shop media, opened directly, never runs in Lotse's origin.
- **Draft preview**: runs in a sandboxed iframe (`sandbox="allow-scripts"`, its own opaque origin). Scripts from AI blocks or shop HTML reach neither the UI nor the API; partial updates and highlight mode go through `postMessage` (`src/lib/preview-frame.ts`). The preview does not send the marker. An approval is `x-lotse: 1` plus optional `LOTSE_PASSWORD`, not a click secret.
- **Sales**: off by default. Only the switch under Settings → AI access → Sales allows `sales_report` and the sales checks. The adapter then reads, with a fixed query built on the server (never with criteria from the AI), only product ID, quantity, line total and the link to the order, and passes on nothing but totals per product. Customers, addresses, order numbers and single orders never reach the AI; the AI's read client still blocks orders. Every read is in the access log (`sales`).
- **Web research**: off by default. Only the switch under Settings → AI access → Internet gives the AI web search and fetching of public web pages (Claude: `WebSearch`/`WebFetch`, Codex: `web_search`); search terms and addresses are sent to the AI provider's search service. The system prompt treats web content as data, not instructions; writing stays bound to approval, shell and file tools stay blocked.
- **Codex (ChatGPT subscription)**: Codex's own tools (shell, files, web, images, plugins) disabled (web search only when web research is on), file access blocked via permission profile (not escalatable), `approval_policy=never`; shop tools only via `/api/mcp/<chat>` with a random token per chat. Blocked tools in the event stream abort the turn immediately.
- **Sandbox Coding**: off by default (Settings → Sandbox; `LOTSE_SANDBOX=0` hard off) and blocked while Lotse is reachable from the network without `LOTSE_PASSWORD`. Docker access is root access to the host: only `src/server/sandbox/runner.ts` talks to Docker, with a closed set of operations and only on containers labelled `lotse.managed=1`. The container spec is built by the server alone (one configured `dockware/shopware:<version>` – or its predecessor `dockware/play:<version>` –, never `latest`, never from AI or chat input; no host paths, no privileges, no devices). In Docker mode a filtering socket proxy only passes containers, images, networks and exec (an additional layer, not the boundary); in both modes the task containers sit only on an internal network without internet and without the live shop, with no published ports (directly on a Linux host Lotse reaches them via their IP on that network; where that is impossible the setup stops instead of falling back to a network with internet). Lotse shares that network with the containers; its subnet is pinned (`LOTSE_SANDBOX_SUBNET`) and Lotse refuses every request from it, so code in a container (own commands, the repository, the shop) never reaches the Lotse API. Without the subnet in Docker mode the sandbox stays blocked unless `LOTSE_PASSWORD` is set. The runner also checks the container spec against an allow-list (exact key spelling, mandatory: the internal network only, no ports). Only the repository's files reach the container, as an archive (never `.git`, `.env*`, keys, `auth.json` or symlinks pointing outside); the git history lives separately. Setup steps are fixed command lines of the template; only the own commands of the environment (maintained by people in the settings, never by the AI) run via `bash -lc`. Logs are redacted before they are stored. The AI never gets Docker access. **Screenshots** are taken by a second, fixed image (`mcr.microsoft.com/playwright:v1.64.0-noble`, only its Chromium): a short-lived container with exactly one fixed script, as a non-root user, without capabilities, with `no-new-privileges`, only on the internal network, without mounts and ports; the job (only the alias of its own sandbox and validated paths) comes from the server, the images come back as an archive and are checked as PNG. They stay in Lotse; none of them reaches GitHub (the pull request only mentions them), and the AI has no tool for them. In a **chat with an attached sandbox** the AI (Claude or Codex) has **no** shop tools: no reading or writing in the live shop, no change sets. A sandbox is only attached by the user’s click (the `start_sandbox` tool only shows a card). It changes files only inside the task’s worktree: Claude with Claude Code’s own tools (`Read`, `Edit`, `Write`, `Glob`, `Grep`), every call checked by a hook and `canUseTool` (realpath inside the worktree, no symlinks to outside, `.git`, `.env*`, keys, `auth.json` and `config/jwt` denied, `vendor/`/`node_modules/` read-only, `Grep` excludes secret files); there is no `Bash`, no subagents and no `NotebookEdit`. Codex writes with its own patches only inside the worktree (permission profile, checked again; otherwise the turn is aborted), its own shell stays off. The AI runs commands only with `sandbox_bash` **inside the container** (any command line, as `www-data`, with a timeout): the container is a disposable shop without internet and without the live shop; nothing ever runs on the Lotse machine. It can neither commit nor push, call GitHub or control Docker (**publishing** only by the user's click: the server fixes branch `lotse/<slug>-<id>` and base, pushes go only to `refs/heads/lotse/*`, a re-push only with `--force-with-lease` on Lotse's own state; changes to `.github/workflows`, `.github/actions` and `action.yml`, protected files and secret-looking content – tokens, private keys, URLs with credentials, secrets stored in Lotse – block before the push; audit before the first write and afterwards, with the user, never with the token); tool output is redacted and capped, `get_environment` names environment variables only. **Feedback on the pull request** (reviews, comments, checks) is read from GitHub read-only and conditionally; it counts as third-party input: redacted, capped, shown as plain text in the chat, and the AI only gets it after the click **Hand over to AI**, marked as data between random delimiters. It never starts a turn, a command or a publish by itself. **Secret variables are visible inside the container; output is redacted:** a command in the container (e.g. `env`) or code the AI writes can read them; redaction only catches plain text and simple encodings (Base64, hex), no guarantee. Secret variables therefore count as visible to the AI and should only hold credentials meant for the sandbox alone. The AI process runs without credentials in its environment; the repository’s `CLAUDE.md`, `AGENTS.md` and `.claude/` are not loaded, repository content counts as data in the prompt. **Database dumps** (sanitized only, without customer data) stay in `<data>/dumps/` until the import (mode 0600, outside every workspace, not in backups, not readable by the AI, no response returns their content) and are deleted right after the import – also after a failed import, when the task is finished, after 24 hours at the latest and by the cleanup after a restart; inside the container the import command deletes them itself. The upload runs in chunks (at most 16 MB, total size `LOTSE_DUMP_MAX_MB`) behind the same login, host check and `x-lotse` marker as every write; the limits apply while receiving. Secret environment variables are encrypted, never shown and stripped from text sent to the AI. Guide: [`docs/en/self-hosting.md`](docs/en/self-hosting.md#enable-sandbox-coding).
- **Sandbox preview** (`/sbx/<id>.<key>/`): the storefront of a task container is AI or repository code and is treated as untrusted. Like the live preview it runs in an opaque origin (CSP `sandbox`, plus `connect-src 'self'`, `form-action 'self'`, `frame-ancestors 'self'`). Lotse forwards only to the container it started for this task (from its own registry, never from the request; no redirects to elsewhere), sends no browser cookies or headers along and passes no sandbox headers or cookies to the browser (a cookie jar per task in the server holds the session). The key in the path (HMAC with the key in the data folder) makes the address unguessable and ties writing requests to the task; `Referrer-Policy: same-origin` keeps it from foreign sites. Requests from preview pages without the prefix end up in the same sandbox, never at the Lotse API.
- **Container**: runs as non-root, read-only file system, no Linux capabilities, `no-new-privileges`, resource limits.

## Recommendations for live shops
1. Create a dedicated Shopware **integration** with a role that may only write the areas needed (products, categories, shopping experiences, media) – do not use an admin user.
2. Test new workflows on a **staging shop** first.
3. Run `make backup` (Lotse data) and shop backups regularly.
