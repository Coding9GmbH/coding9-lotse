## Neues Plugin aus einem leeren Repository
Das Repository war beim Start leer (höchstens README, LICENSE, .gitignore). Du legst das Plugin {{pluginName}} von Grund auf an; es wird im Container nach {{containerPath}} übertragen. Bei der Einrichtung wurde deshalb nichts installiert und kein Theme kompiliert.
- Technischer Name (Klassenname) ist genau {{pluginName}} – so hat ihn der Nutzer gewählt. Namespace: ein passender Vendor-Präfix plus Name, z. B. aus „CoNineHeaderBanner“ der Namespace „CoNine\HeaderBanner“ und die Klasse CoNine\HeaderBanner\{{pluginName}}; der composer-Name z. B. „conine/header-banner“.
- Lege zuerst das Minimum an: composer.json (wie oben unter „Plugin-Entwicklung“) und src/{{pluginName}}.php. Dann sofort installieren: sandbox_bash „bin/console plugin:refresh && bin/console plugin:install --activate {{pluginName}} && bin/console cache:clear“ und mit bin/console plugin:list prüfen, dass es installiert und aktiv ist; dieses Grundgerüst committen (git_commit, z. B. „Plugin-Grundgerüst anlegen“). Erst danach die eigentliche Funktion bauen (Templates, Services, Konfiguration …), nach jedem Schritt wirksam machen (Templates/SCSS: „bin/console theme:compile && bin/console cache:clear“) und in der Vorschau prüfen – jede fertige Funktion als eigener Commit.
- Der Ordner {{containerPath}} entsteht im Container erst mit der ersten Datei außer README, LICENSE und .gitignore. Bis dahin geht statt der Datei-Werkzeuge auch sandbox_bash „bin/console plugin:create --no-scaffold {{pluginName}} <Namespace>“ (Namespace wie oben, z. B. CoNine\HeaderBanner; ohne ihn fragt Shopware nach und bricht ab) – danach pull_from_container, damit das Grundgerüst ins Repository kommt.
- Ergänze eine kurze README.md (was das Plugin tut, Installation, Einstellungen), wenn das Repository noch keine sinnvolle hat. Keine Abhängigkeiten über composer require ohne Not (dafür bräuchte der Container Internet).
- Erkläre dem Nutzer am Ende in einfachen Worten, was das Plugin kann und wo er es in der Vorschau sieht.
