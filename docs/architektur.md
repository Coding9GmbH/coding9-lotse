# Architektur

Wie Lotse intern funktioniert: Ablauf einer Chat-Runde, Schutzschichten, Datenhaltung, Vorschau, Layout-Veröffentlichung, Shop-Check, Prompts, Mehrsprachigkeit und Tests. Bedienung steht im [Benutzerhandbuch](benutzerhandbuch.md), die Plattform-Schnittstelle in [platform.md](platform.md).

## 1. Überblick

```
Browser ──► proxy.ts ──► Next.js (App Router)
              │            ├─ app/api/**        REST + Chat-Stream (NDJSON)
              │            ├─ app/shop/**       Storefront-Proxy für die Vorschau
              │            └─ Oberfläche        React 19, ein Reducer (lib/chat-state.ts)
              │
              └─ Host-/Origin-Prüfung, Login, Storefront-Pfade → /shop

Chat-Runde:  Agent (Claude SDK | Codex) ──► Werkzeuge (tools.ts) ──► geschützter Lese-Client ──► Shop
                                   │
                                   └─► propose_* / publish_page ──► Änderungsset ──► Freigabe (Mensch)
                                                                                      │
                                              Executor (changes.ts, einziger Schreiber) ◄┘
                                              ├─ Audit-Log + Rückgängig-Schritte (SQLite)
                                              └─ Shop (privilegierter Client)
```

Stack: Next.js 16 · React 19 · TypeScript (strict) · SQLite (`node:sqlite`) · Claude Agent SDK oder OpenAI Codex SDK. Lauffähig als Docker-Image (`output: 'standalone'`) oder `npm run dev`.

## 2. Ablauf einer Chat-Runde

1. **Start.** `POST /api/chat` startet eine Runde und antwortet als NDJSON-Stream, eine JSON-Zeile je Ereignis (`ChatEvent`, Typen in `lib/protocol.ts`). Die Runde läuft **serverseitig weiter**, auch wenn die Verbindung abbricht oder der Chat gewechselt wird. `GET /api/chat` verbindet wieder: erst ein `snapshot` des bisherigen Verlaufs, dann die Live-Ereignisse.
2. **Prompt.** `prompt.ts` setzt den System-Prompt aus `prompts/common/*.md` und `prompts/<plattform>/*.md` zusammen (Platzhalter wie `{{shop}}`), dazu der Styleguide-Block, die Regeln (`rulesPromptBlock`), die Antwortsprache (`REPLY_LANGUAGE`, Abschnitt 12) und bei Kontext ein Ziel-Hinweis (`target-hint.ts`).
3. **Werkzeuge.** Der Agent bekommt die Werkzeuge der Plattform und der Feature-Module (`tools.ts`, `features/`). Lesen läuft über den geschützten Lese-Client; **Schreiben gibt es nicht**, nur Vorschläge (`propose_*`, `publish_page`).
4. **Rückfragen.** `ask_user` erzeugt ein `question`-Ereignis; die Runde wartet, `POST /api/answer` setzt sie fort.
5. **Vorschlag → Freigabe.** Ein Vorschlag wird zu einem `ChangeSet` (Zeilen mit vorher/nachher, Warnungen, Auswahl). Das Werkzeug wartet auf die Entscheidung; `POST /api/approve` übergibt Freigabe und gewählte Zeilen.
6. **Schreiben.** Der Executor schreibt die gewählten Zeilen gedrosselt, hält je Zeile einen Rückgängig-Schritt fest und trägt das Ergebnis ins Audit-Log ein. `POST /api/changesets/undo` nimmt eine Anwendung zurück.
7. **Ende.** `done` schließt die Runde ab; offene Schritte werden in der Oberfläche abgeschlossen.

### Anbieter
- **Claude** (Agent SDK, In-Process-MCP-Server `shop`): Werkzeuge im selben Prozess.
- **Codex** (ChatGPT-Abo): eigene Codex-Werkzeuge (Shell, Dateien, Web) abgeschaltet, Dateizugriff per Profil gesperrt; Shop-Werkzeuge nur über `/api/mcp/<chat>` mit Zufalls-Token je Chat.

### Chats mit Sandbox (Sandbox Coding)
Eine Sandbox ist eine Entwicklungsumgebung mit Git-Anbindung, in der Claude Code oder Codex arbeiten: Arbeitskopie des Repositorys, lokale Commits der KI, ein eigener Test-Shop im Container; Push und Pull Request nur per Klick. Sie hängt an einem normalen Chat der Arbeitsfläche (`code_tasks.chat_id`; höchstens eine nicht abgeschlossene je Chat, `attachedTask`). Angehängt wird sie nur durch den Nutzer (`POST /api/sandbox/tasks` mit `chatId`, aus dem Dialog „Sandbox starten“ oder der Karte des Werkzeugs `start_sandbox`, das die KI in normalen Chats bei eingeschaltetem Sandbox Coding hat und das nur ein `sandbox_offer` zeigt). `Session.taskId` wird zu Beginn jeder Runde neu bestimmt: Mit Sandbox bekommt die Runde **nur** die Sandbox-Werkzeuge – keine Shop-Werkzeuge, kein Live-Shop – und den Prompt aus `prompts/code/01-common.md` + `prompts/code/<vorlage>.md` (mit Arbeitsordner, Titel/Ziel als zitierte Daten). Die KI-Sitzung gehört zu Arbeitsordner und Werkzeugsatz: Wechselt die Sandbox (anhängen, abschließen), startet `agent.ts` eine neue Sitzung mit einer kurzen Zusammenfassung des bisherigen Verlaufs (`agentScope`, `recapOf`). Vor jeder Runde prüft `prepareCodeTurn`, dass Sandbox Coding an ist, wartet auf eine laufende Einrichtung und weckt einen pausierten Container (`sandbox_status`); während der Runde pausiert der Leerlauf-Sweeper ihn nicht. **Claude** arbeitet mit den eigenen Werkzeugen von Claude Code `Read`, `Edit`, `Write`, `Glob`, `Grep`, `TodoWrite` mit `cwd` = Arbeitsordner (Bash, Task, NotebookEdit nie; Web nur mit Internetrecherche); jeder Aufruf läuft durch einen `PreToolUse`-Hook und `canUseTool` (`sandbox/native-tools.ts`: jeder Pfad realpath-geprüft im Arbeitsordner, `.git`/Geheimnisse/`config/jwt` gesperrt, Schreiben nicht in `vendor/`/`node_modules/`, Pfade mit `~` abgelehnt, `Grep` bekommt den Ausschluss der geheimen Dateien als letztes glob angehängt); nach `Edit`/`Write` überträgt ein `PostToolUse`-Hook die Datei in den Container und zeigt sie als `file_change`. **Codex** läuft mit `workingDirectory` = Arbeitsordner, `workspace-write` (Profil: nur der Arbeitsordner beschreibbar, `.git` gesperrt), ohne Netz und ohne eigene Shell; seine Patches (`file_change`) gelten nur, wenn alle Pfade im Arbeitsordner liegen und erlaubt sind; abgelehnte Pfade setzt `revertPaths` zurück (aus `HEAD` bzw. gelöscht), dann bricht die Runde ab; die übrigen werden übertragen. MCP-Werkzeuge (`sandbox/workspace-tools.ts`): `sandbox_bash` (beliebige Befehlszeile per `bash -lc` als `www-data` in `/var/www/html` **im Container**, vorher vollständiger Abgleich, unter der Sperre der Aufgabe, Zeitlimit 120 s/max. 600 s, Ausgabe redigiert und auf 12 KB gekürzt; nach `theme:compile`/`cache:clear` u. a. `preview_reload`), `delete_file`, `git_diff` (Netto-Diff gegen den Basis-Branch, dazu die lokalen Commits und was noch nicht committet ist), `git_commit` (ein lokaler Commit wie in Claude Code: alle Änderungen oder `paths`, Nachricht von der KI – erste Zeile ≤ 120, gesamt ≤ 2000 Zeichen, Steuerzeichen entfernt; Pfade literal (`--literal-pathspecs`), relativ, ohne `..`/`.git`/führendes `-`; keine Geheimnisse in der Nachricht; dieselbe Prüfung wie beim Veröffentlichen für genau die bereitgestellten Inhalte (`commitCheck` auf den Blobs im Index, im selben Schritt der Index-Warteschlange wie der Commit – eine parallel geschriebene Datei kommt nicht ungeprüft hinein, eine Ablehnung setzt den Index auf `HEAD` zurück: geschützte Dateien, Workflows, Größen, Geheimnis-Suche – ohne Freigabe, denn Commits werden später unverändert gepusht und nie umgeschrieben); `git.ts` `commitChanges` fügt nur einen Commit auf `HEAD` hinzu: kein Push, kein Amend/Rebase/Reset, kein Branch-Wechsel, keine Hooks, Autor `Lotse`, angemeldeter Nutzer als Co-Autor), `read_sandbox_page`, `get_environment` (Variablen nur mit Namen), `ask_user`, `request_internet` (Karte `internet_request`, wartet wie ein Änderungsset auf die Entscheidung über `/api/approve`; erst die Zustimmung hängt den Container per `sandbox/internet.ts` an das Netz `lotse-sandbox-egress`), `propose_publish`; Codex zusätzlich `list_files`, `read_file`, `search_files`. Claude läuft ohne `settingSources`, mit höchstens 120 Schritten, unter der Kostenbremse. Rechts zeigt `Workspace.tsx` statt der Entwurfsvorschau `SandboxPanel` (Statuszeile, Reiter Vorschau/Einrichtung/Änderungen/Freigabe = Pull Request/Konsole). Ehemalige getrennte Code-Chats (`mode: 'code'`) sind dadurch Chats mit angehängter Sandbox; ihre alte KI-Sitzung wird nicht fortgesetzt.

**Konsole** (`sandbox/console.ts`, Reiter „Konsole“, `ConsolePanel.tsx` mit xterm.js): eine Shell im Container nur für den Nutzer, nie ein KI- oder MCP-Werkzeug. Route-Handler können keine WebSockets, daher hält der Server je Sitzung den gekaperten Exec-Stream (`SandboxRunner.openTty`: `POST /containers/{id}/exec` mit `Tty`, `exec/{id}/start` mit Upgrade, Größe über `exec/{id}/resize`; Label-Prüfung vorher). Der Browser liest die Ausgabe per `GET /api/sandbox/tasks/<id>/console/<sitzung>?from=<n>` (NDJSON, nummerierte Base64-Stücke; die letzten 256 KB bleiben für ein Wiederverbinden nach dem Neuladen) und schickt Eingaben und Größe per `POST` (höchstens 64 KB), `DELETE` schließt. Die Shell kommt aus der Vorlage (`ConsoleSpec`: Dockware als `dockware` in `/var/www/html`, `TERM=xterm-256color`). Weil die Befehle der KI dieselbe uid 33 haben, startet ein Wrapper als root, schreibt Startdatei und PID samt Startzeit (= Sitzungs-ID der TTY) nach `/run/lotse-console/` (nur root schreibbar) und wechselt per `setpriv` zu `dockware`: `bash --noprofile --rcfile /run/lotse-console/bashrc -i` liest nur `/etc/bash.bashrc` und `/etc/profile`, kein `~/.bash_profile`/`~/.bashrc`/`~/.inputrc`, keinen Verlauf, ohne `BASH_ENV`. Schließen beendet die ganze Sitzung (`pkill -s`, als root – auch was per sudo lief), aber nur, wenn PID und Startzeit noch passen. Sitzungs-IDs sind zufällig und je Aufgabe und Login-Name getrennt (Komfort, keine Zugriffsgrenze); höchstens drei je Aufgabe, zwei Ausgabe-Streams je Sitzung. Die Ausgabe ist auf 1 MB/s begrenzt (`TtySession.pause`/`resume` am Docker-Socket), Base64 nur, solange jemand zusieht; eine Ansicht mit mehr als 1 MB in der Warteschlange (`desiredSize`) wird getrennt und verbindet sich ab ihrem letzten Stück neu, die Lücke markiert `ConsolePanel`; Öffnen weckt eine pausierte Sandbox, Eingaben zählen als Aktivität. Geschlossen wird nach 30 Minuten ohne Eingabe (Sweeper), beim Pausieren (`stopContainer`; scheitert `docker stop`, beendet `endConsoleShells` die Shells), bei einer neuen Einrichtung (`runSteps`), beim Abschließen und Ausschalten; nach einem Neustart beendet der Abgleich verwaiste Shells; eine Konsole, die gerade startete, als die Sandbox pausiert oder geschlossen wurde, wird danach mit diesem Grund geschlossen. Audit: geöffnet/geschlossen mit Grund, keine Tastendrücke. Im Test und E2E antwortet `FakeRunner.openTty` als kleine Echo-Shell.

**Veröffentlichen** (`server/sandbox/publish.ts`, `POST /api/sandbox/tasks/[id]/publish`): nur per Klick im Reiter „Freigabe“ (Pull Request); der Body hat nur Titel (≤ 200) und Beschreibung (≤ 20 000), Branch (`lotse/<slug>-<id>`, beim Anlegen festgelegt) und Basis kommen aus der Aufgabe. Die KI kann mit `propose_publish` nur eine Karte (`publish_proposal`) zeigen. Ablauf: eine Sperre je Aufgabe (`markPublishing`; zweiter Klick, laufende KI-Runde oder „Sandbox abschließen“ → 409, eine neue KI-Runde wartet), Vorprüfung (Änderungen vorhanden, höchstens 300 Dateien/5 MB je Datei/25 MB, keine Pfade außerhalb, kein `.github/workflows`/`.github/actions` und kein `action.yml` (lokale Actions laufen mit den Secrets des Repositorys), keine geschützten Dateien, keine Symlinks nach außen, Geheimnis-Suche in allen gegenüber dem Basis-Branch und dem zuletzt gepushten Stand neuen Zeilen der Dateien auf der Platte – Tokens, private Schlüssel, Adressen mit Zugangsdaten und die in Lotse gespeicherten Geheimnisse, plausibel geheime (`secret-values.ts`: kein gängiges Wort oder Paketname, lang oder gemischt genug) als eigenes Token überall, schwache („sommer2024“, „shopware“) nur als Wert eines Zugangsdaten-Schlüssels (`password => …`, `DB_PW=…`, `-p…`), jeweils nicht schon im Basis-Stand der Datei; Titel und Beschreibung ebenso, dazu die Nachrichten der noch nicht gepushten lokalen Commits (ohne Freigabe). Funde nennen Datei und Zeile (`task.publish.findings`); gespeicherte Werte und Adressen mit Zugangsdaten kann der Nutzer mit „Trotzdem veröffentlichen“ freigeben (`allowFindings`: Hash aus Datei und Zeileninhalt, im Audit `secretOverride` mit Datei, Zeile und Art), Schlüssel und Tokens nicht), Audit `kind: 'code-pr', status: 'started'`, `commitAll` nur für noch nicht Committetes (die Commits der KI werden unverändert gepusht; Autor `Lotse <lotse@users.noreply.github.com>`, angemeldeter Nutzer als `Co-Authored-By` mit Adresse unter `.invalid`), `pushBranch` (nur `refs/heads/lotse/*`, beim erneuten Push `--force-with-lease` auf den gespeicherten `pushed_sha` – ist der Branch auf GitHub gelöscht (etwa nach dem Mergen), wird er ohne Lease und ohne Force neu angelegt –, der sofort nach dem Push gesichert wird), dann ein offener Pull Request mit `head=<owner>:<branch>` wird wiederverwendet (PATCH von Titel und Beschreibung), sonst `POST /pulls` (nicht als Entwurf). `pr_number`, `pr_url` und `pushed_sha` stehen in `code_tasks`, der Fortschritt in `task.publish` (`check` → `commit` → `push` → `pr`, bei Fehler mit der Ursache in der Sprache der Anfrage: eine Zeile, darunter gits bzw. GitHubs vollständige Meldung; nur eine echte 403 von GitHub wird zum Token-Hinweis, Branch-Schutz, ein veränderter Branch und andere Ablehnungen des Servers haben eigene Texte, `pushErrorText`); ein Neustart macht aus `running` `interrupted` (`interruptStale`). Ein erneuter Versuch ist idempotent (nichts Neues zu committen, Push entfällt, offener Pull Request wird gefunden – auch nach einer verlorenen Antwort auf das Anlegen). Danach Audit-Ergebnis (`status: 'applied'`, Repository, Branch, Link, Dateien; Fehler `failed`, Sperre der Vorprüfung `decision: 'rejected'`), das Chat-Ereignis `pr` (sofort gespeichert) und `GET …/pr` für Status, Entwurf und Checks des Head-Commits (45 s im Speicher zwischengespeichert). Weil gits Ausgaben redigiert werden, prüft die Geheimnis-Suche die Dateien selbst, nicht den Patch, und vergleicht sie byteweise mit dem unredigierten Stand des Basis-Branches (`readBaseBlob`).

**Rückmeldungen zum Pull Request** (`server/sandbox/pr-watch.ts`): ein Poller je Prozess (`unref`, alle 2 Minuten, gestartet mit dem Leerlauf-Sweeper), nur für Aufgaben mit Pull Request, nicht abgeschlossen, PR nicht gemergt/geschlossen, Sandbox Coding an und GitHub verbunden; nie zwei Runden gleichzeitig. Alle Lesezugriffe sind bedingt (`If-None-Match` mit der ETag im Speicher; 304 kostet kein Anfragelimit): der Pull Request (Status, Head-Commit), Reviews, Zeilenkommentare, Kommentare am Pull Request und die Check-Runs des Head-Commits (je die ersten 100). Neue Einträge – Reviews mit Freigabe/Änderungswunsch/Text, Kommentare mit Text, Check-Runs mit `failure`, `timed_out`, `cancelled`, `action_required` – werden über ihre ID in `task.prWatch.seen` (höchstens 2000, überlebt Neustarts) dedupliziert, redigiert, von Steuer- und Bidi-Zeichen befreit und gekürzt (4000 Zeichen je Text, 30 je Karte) und als **ein** Chat-Ereignis `pr_feedback` gespeichert (`noteChatEvent`) und über den Aufgaben-Stream (`TaskEvent` `chat`) an eine offene Arbeitsfläche geschickt (der Reducer fasst gleiche IDs zusammen). Gemergt/geschlossen: `pr_feedback` mit `state`, `prWatch.state` beendet das Abfragen, `pr.state` erscheint in der Aufgabenliste. Der Poller startet weder eine Runde noch einen Befehl noch ein Veröffentlichen. **An KI übergeben** schickt `POST /api/chat` mit `prFeedback: <id>`; der Server sucht die Karte im Chat (nur für die angehängte Sandbox, sonst eine Fehlermeldung), markiert sie als übergeben und hängt sie hinter den Text des Nutzers als Daten an den Prompt (`feedbackPrompt`): zwischen `<pr-feedback-<zufall>>`-Trennern, Trenner-ähnlicher Text darin entschärft, erneut redigiert, höchstens 24 000 Zeichen, mit dem Hinweis, dass es keine Anweisungen sind. Im Verlauf steht nur der Satz des Nutzers. Eine neue Runde weckt den Container wie jede andere; veröffentlicht wird wieder nur über `publish.ts`.

**Ohne Entwickler** (A15): Die Oberfläche der Sandbox spricht Klartext – „Änderung speichern“ (Commit), „Zur Prüfung freigeben“ (Pull Request), „Projekt“ (Repository); der Fachbegriff steht klein daneben (`Term.tsx`) oder im Tooltip. Ein leerer Sandbox-Chat zeigt Beispiel-Aufträge als Chips, und der Prompt verlangt am Ende eine Erklärung in einfachen Worten samt Seite in der Vorschau. **Neues Projekt** (`GET/POST /api/sandbox/repos`, `github.ts` `listRepoOwners`/`createRepo`): Besitzer sind der Nutzer des Tokens und seine Organisationen (`/user/orgs`, Fehler → nur der Nutzer); angelegt wird per `POST /user/repos` bzw. `/orgs/{org}/repos` ein privates Repository mit `auto_init` (README auf `main`, damit es einen Basis-Branch hat und trotzdem als leer gilt – die Einrichtung macht daraus ein neues Plugin). Name nach GitHubs Regeln (`REPO_NAME`, auch im Dialog), unbekannter Besitzer 400, Name vergeben (422 „already exists“) 409, 403/404 von GitHub → 403 mit der nötigen Berechtigung („Administration: Lesen & Schreiben“, klassisch Scope `repo`); danach prüft `checkRepoAccess`, dass der Token das neue Repository sieht. Audit `kind: 'github-repo'`. **Plugin als ZIP** (`server/sandbox/plugin-zip.ts`, `server/zip-write.ts`, `GET /api/sandbox/tasks/[id]/plugin-zip`, `?check=1` nur die Prüfung): aus der Arbeitskopie, wie sie auf der Platte liegt (auch nicht Committetes), solange die Sandbox nicht abgeschlossen ist (sonst 409). `composer.json` wird zuerst geprüft – Probleme sperren den Download (422 mit der Prüfung): alles, ohne das Shopware 6.7 ein hochgeladenes Plugin gar nicht erst aufführt – geprüft gegen Dockware 6.7.15.1, wo `plugin:refresh` solche Plugins stillschweigend übergeht (`type`, `name` und `version` nach composers eigenen Mustern, `description`, `autoload` psr-4/psr-0, `extra.shopware-plugin-class`, `extra.label` als Objekt – ein String-Label bricht dort sogar die ganze Plugin-Liste) –, dazu `noComposer`, `badJson`, `pluginName`, `empty`, `tooLarge`, `secret`. Hinweise (`requireCore`, `classFile`, `vendorMissing`) sperren nicht. Oberster Ordner = technischer Name aus `extra.shopware-plugin-class` und erster Eintrag (Shopwares Upload liest `<Name>/composer.json` aus dem Ordner des ersten Eintrags). Ausgelassen: `.git`, `node_modules`, `tests`/`Tests`, `.github`, `.gitlab`, IDE-Ordner, `.env*`, alles, was `isDenied` sperrt (Schlüssel, `auth.json`, `config/jwt`), Entwicklungsdateien (`phpunit.xml*`, `.gitignore` …), Symlinks; `vendor/` nur, wenn `require` mehr als `php`, `ext-*`, `shopware/*`, `composer/*` verlangt und `vendor/autoload.php` existiert. Höchstens 5 000 Dateien/100 MB; Textdateien bis 2 MB laufen durch die Geheimnis-Suche, Schlüssel und Tokens (nicht freigebbar) verhindern das ZIP. Der eigene ZIP-Schreiber (deflate oder gespeichert, UTF-8-Namen, CRC per `zlib.crc32`, kein ZIP64) liefert Eintrag für Eintrag als Web-Stream; jeder Download steht als `action: 'zip'` mit Name, Version, Dateizahl, Größe und `vendor` im Audit. In den Live-Shop installiert Lotse nichts.

**Screenshots, nur von Hand** (`server/sandbox/screenshots.ts`, `screenshot-spec.ts`): weder ein Einrichtungsschritt noch ein Schritt beim Veröffentlichen. Mit dem Schalter `screenshots` der Umgebung (Standard aus) zeigt die Vorschau „Screenshot“; `POST /api/sandbox/tasks/[id]/screenshots` (nur bei laufender, bereiter Sandbox, einer zur Zeit je Aufgabe, 409 sonst; währenddessen pausieren weder Leerlauf-Sweeper noch `LOTSE_SANDBOX_MAX` den Container) nimmt die Seiten aus `screenshotPaths` (höchstens 5, Standard `/`, Pfade geprüft) je auf Desktop (1366 px) und Mobil (390 px) auf und hängt den Satz an `task.shots` (höchstens 6, der älteste fliegt samt Dateien; ein neuer Klon löscht alle). Aufgenommen wird in einem kurzlebigen Container des zweiten festen Images `mcr.microsoft.com/playwright:v1.64.0-noble` (Runner-Positivliste: genau dieser Befehl `node /lotse/shot.mjs`, Nutzer `pwuser`, `CapDrop: ALL`, `no-new-privileges`, nur `lotse-sandbox`, keine Mounts, keine Ports, Label `lotse.role=screenshot`). Skript und Auftrag (`job.json`, vom Server gebaut) kommen per `putArchive`, dann `start`, `wait`, `getArchive /lotse/out` (höchstens 48 MB) und `remove`. Das Skript startet je Aufnahme `chrome-headless-shell --screenshot` mit dem Sandbox-Alias `lotse-sbx-<id>` als HTTP-Proxy und `http://localhost/<pfad>` als Adresse (Dockware antwortet nur auf `Host: localhost`), ohne Shell. Lotse übernimmt nur die erwarteten Dateinamen mit PNG-Signatur (höchstens 8 MB) nach `<Daten>/screenshots/<id>/<satz>-<n>-<gerät>.png`; `GET /api/sandbox/tasks/[id]/screenshots/[file]` liefert nur Dateien, die die Aufgabe aufführt (`nosniff`). Schlägt eine Aufnahme ganz fehl, wird nichts gespeichert (502 mit Grund). Der Reiter „Freigabe“ zeigt die Sätze nur, wenn es welche gibt; der Pull-Request-Text erwähnt sie nur (ohne Link, kein Upload zu GitHub); die KI hat kein Werkzeug dafür.

**Weitere Vorlagen** (`server/sandbox/templates/`): Vorlagen sind Code, nie Konfiguration. Jede hat eine Laufzeit (`runtime`): `container` (Dockware – Image, feste Schritte, Befehle der Positivliste, Container-Spezifikation; Vorschau über `/sbx`, `previewProvider: { kind: 'sandbox' }`) oder `none` (kein Container, keine Befehle, keine Einrichtungsschritte; die Plattform zeigt die Vorschau selbst, `previewProvider: { kind: 'platform' }`). `REGISTRY` führt alle Vorlagen, `TEMPLATES` nur die eingeschalteten mit Container – nur `dockware` läuft. Vorbereitet und **ausgeschaltet** ist `shopify-theme`: Das Repository ist ein Theme (`layout/theme.liquid`, `config/settings_schema.json`), die KI bearbeitet es wie gewohnt im Arbeitsordner; ein späterer, nur per Klick ausgelöster Ausführer würde den Arbeitsordner in ein **von Lotse angelegtes, unveröffentlichtes** Theme schieben (`target: 'unpublished-theme'`) und die Vorschau als `https://<shop>.myshopify.com/?preview_theme_id=<id>` zeigen (Adresse nur aus Server-Werten, Shop-Domain und ID geprüft). Das Live-Theme wird nie geschrieben; Befehle in einem Container gibt es bei dieser Laufzeit nicht. Bis dieser Ausführer existiert, lehnt `getTemplate` die Vorlage ab.

## 3. Schutzschichten

| Schicht | Wo | Wirkung |
|---|---|---|
| Host-/Origin-/Kennungsprüfung | `proxy.ts` | Nur freigegebene Hostnamen; Loopback-Namen nur von Loopback (im Container zusätzlich private Gateway-Adressen bei Loopback-Publish); `Origin` muss zu `Host` passen; schreibende Aufrufe brauchen `x-lotse: 1` |
| Login | `proxy.ts` | `LOTSE_PASSWORD` → Basic Auth (zeitkonstanter Vergleich), `/api/mcp/*` hat eigenes Token, `/api/ping` offen |
| Lese-Client mit Freigabeliste | `policy.ts` + Reader je Plattform | Nur freigegebene Entitäten/Beziehungen/Felder; Kunden-, Bestell-, Zahlungs- und Zugangsdaten gesperrt; Bereiche aus den Einstellungen; jeder Zugriff im Zugriffsprotokoll |
| Nur Vorschläge | `tools.ts`, `changes.ts` | Werkzeuge der KI enthalten kein Schreiben; Executor ist die einzige Schreibstelle |
| Freigabe + Audit + Rückgängig | `changes.ts`, `audit.ts` | Alt→Neu, Zeilenauswahl, Protokoll, Undo je Zeile |
| Shop-Schonung | `changes.ts`, Clients | Drosselung (`LOTSE_WRITE_CONCURRENCY`), max. 300 Einträge je Set (`MAX_ITEMS`), Timeouts, Backoff bei 429/503 |
| Zugangsdaten | `db.ts` | AES-256-GCM, Schlüssel `secret.key` im Datenvolume, nie an die KI, aus Fehlertexten entfernt |

## 5. Vorschau

Drei Darstellungen, alle ohne Zugriff auf Lotse:

| Darstellung | Quelle | Isolation |
|---|---|---|
| **Aktuell** | Shop-Seite über den Proxy `/shop/…` im iframe | `sandbox="allow-scripts allow-forms"` (kein `allow-same-origin`) und CSP `sandbox allow-scripts allow-forms; script-src 'self' 'unsafe-inline'; object-src 'none'; base-uri 'self'` per Antwort-Header: opaker Origin auch bei direkter Navigation, keine Drittanbieter-Skripte |
| **Sandbox** (Sandbox Coding) | Storefront des Aufgaben-Containers über `/sbx/<id>.<schlüssel>/…` | wie **Aktuell**, dazu `connect-src 'self'; img-src 'self' data:; form-action 'self'; frame-ancestors 'self'` |
| **Entwurf** (einfach) | `renderPreview` in `cms.ts` rendert die Spec im Theme-CSS des Shops | `srcdoc`, `sandbox="allow-scripts"` |
| **Entwurf auf der echten Seite** (Shopware) | echte Zielseite, nur `.cms-sections` ersetzt | wie Entwurf |
| **Entwurf im echten Theme** (Shopify, Magento, OpenMage) | echte Zielseite, veröffentlichtes HTML im Inhaltsbereich (`theme-preview.ts`) | wie Entwurf |

**Proxy `/shop`** (`app/shop/[[...path]]/route.ts`): ruft die Storefront über die interne Adresse ab, schreibt Shop-URLs auf `/shop` um, entfernt Cookies und Frame-Sperren, setzt die CSP, injiziert das Rahmen-Skript (`lib/preview-frame.ts`, Markieren, Scroll, per `postMessage`) und gibt Bilder/Schriften mit CORS frei. Weiterleitungen: gleiche Herkunft als `/shop`-Pfad; gleiche Site (Eltern-Domain, z. B. `stage.` → `www.`) serverseitig gefolgt (höchstens 3 Hops); fremde Domains nie. Wurzelrelative Pfade des Shops (`/theme`, `/media`, `/thumbnail` …) leitet `proxy.ts` an `/shop` um. Gemeinsame Teile (Header, CSP, Umschreiben, Rahmen-Skript) liegen in `server/storefront-proxy.ts`.

**Proxy `/sbx`** (`app/sbx/[task]/[[...path]]/route.ts`, `server/sandbox/preview.ts`): Vorschau der Storefront einer Code-Aufgabe, zum Testen bedienbar (GET/HEAD/POST/PUT/PATCH/DELETE, Body höchstens 2 MB). Das Ziel kommt nur aus Lotses eigenem Eintrag für den Container, den es gestartet hat (Alias im Netz `lotse-sandbox` bzw. der von Docker gemeldete Port auf `127.0.0.1`), nie aus der Anfrage; Anfragen gehen mit `Host: localhost` hinaus, Weiterleitungen gibt Lotse nur innerhalb der Sandbox als `/sbx`-Pfad zurück und folgt ihnen nicht selbst. Die Seite läuft in einem opaken Origin: Der Browser schickt weder Cookies noch Referer. Darum trägt der Pfad einen Schlüssel (HMAC der Aufgaben-ID mit dem Schlüssel im Datenordner), der Formular- und Ajax-Anfragen an die Aufgabe bindet (falscher Schlüssel = 404), Cookies der Sandbox hält Lotse in einer Keksdose pro Aufgabe im Speicher (nie an den Browser), und ein kleines Skript am Anfang von `<head>` ersetzt `document.cookie` (lesbare Cookies aus der Keksdose, Schreiben per `sendBeacon` an `…/__lotse/cookie`) und Web Storage (im Speicher) und hält `fetch`/XHR-Pfade unter dem Präfix. Absolute Adressen `http://localhost` und wurzelrelative Pfade in HTML/CSS werden auf das Präfix umgeschrieben; Anfragen aus einem Vorschau-Stylesheet ohne Präfix leitet `proxy.ts` anhand des Referers in dieselbe Sandbox. Eine pausierte Aufgabe weckt der Aufruf („Umgebung startet …“ mit automatischem Neuladen); jeder Aufruf zählt als Aktivität.

**Entwurf auf der echten Seite** (`real-page.ts`, `platform/shopware/pages.ts`):
1. `previewData` lädt die Zielseite (`/detail/{id}`, `/navigation/{id}`, höchstens 2 Weiterleitungen, nur im Shop, 12 s, 1,5 MB, 60 s Zwischenspeicher).
2. `stripScripts` entfernt Kommentare sowie Skripte und Vorladehinweise fremder Domains; Shop-Skripte bleiben.
3. `extractBlocks` zieht die echten dynamischen Blöcke heraus (Kaufbox, Überschrift, Beschreibung/Bewertungen, Cross-Selling, Produktliste, Filter), auch für Themes mit eigenen Blocktypen (Markup-Erkennung).
4. `renderPreview` setzt Entwurf und echte Blöcke in `.cms-sections` ein (`spliceSections`). Findet es den CMS-Bereich nicht, fällt es auf die einfache Darstellung zurück.
5. Ohne genanntes Ziel wählt `withPreviewDefaults` ein aktives Produkt mit Titelbild.

**Entwurf im echten Theme** (`theme-preview.ts`, HTML-Plattformen): Zielseite über `lookup.entityPaths` (Produkt, Kategorie/Kollektion) bzw. die Startseite bei Landingpages, Abruf wie oben (Weiterleitungen nur im Shop, 12 s, 1,5 MB, 60 s Zwischenspeicher, `stripScripts`, Shop-URLs auf `/shop`). Inhaltsbereich ist `<main>` (Shopify, Magento 2) bzw. `.col-main` (OpenMage); dort setzt `spliceMain` `renderPageParts` vor und hinter den Theme-Inhalt, Landingpages ersetzen ihn (`renderPageHtml`). Produktinhalte ohne `theme-main` (Magento, OpenMage) landen wie beim Veröffentlichen in der Produktbeschreibung (`.product.attribute.description .value` bzw. `.box-description .std`). Protokoll-relative Shop-Adressen (`//host/…`, Shopify) gehen ebenfalls über `/shop`, damit die Theme-Skripte erhalten bleiben. Beim Streaming nur aus dem Zwischenspeicher; ohne Inhaltsbereich die einfache Darstellung.

Streaming: Beim Schreiben schickt der Server `draft_partial` (nur `<body>` per `postMessage`, Theme-CSS und Scroll bleiben), danach `draft` (Dokument neu, Scroll wiederhergestellt). `PREVIEW_VERSION` (`tools.ts`) erzwingt beim Laden eine Neuerzeugung gespeicherter Entwürfe.

## 6. Layouts veröffentlichen (Shopware)

`publish_page` → `buildPublish` (`platform/shopware/pages.ts`) → `buildPublishChangeSet` (`changes.ts`) → Applier `applyPublish`.

1. **Bereich auflösen.** `resolvePublishScope` macht aus `allCategories`, `allProducts`, `productsInCategoryId` usw. feste ID-Listen (Seiten à 500, Deckel `SCOPE_MAX = 1000`). Mehrdeutige Angaben werden abgewiesen. Produkte: aktive Hauptprodukte (Varianten erben). Kategorien: Typ `page`, ohne Wurzel.
2. **Änderungsset.** Bis 15 Ziele eine Zeile je Ziel; darüber eine Zusammenfassung („N, davon M mit eigenem Layout, wird ersetzt“) plus Bereich und 8 Stichproben. Meta-Daten nur bei einer einzelnen Kategorie.
3. **Anwenden.** Layout (`cms-page`) anlegen, dann Zuweisungen mit begrenzter Parallelität; beim ersten Fehler startet kein weiteres Ziel, alles wird zurückgenommen (atomar). Je Ziel ein Undo-Schritt mit dem vorherigen `cmsPageId`.
4. **Zwischenstände.** `trackedUndo` meldet jeden Schritt sofort; ein Absturz verliert kein Rückgängig.

Andere Plattformen veröffentlichen über ihre eigenen Pfade (Shopify: Theme-Vorlagen, Magento/OpenMage: CMS-Seiten bzw. Page Builder), siehe [platform.md](platform.md).

## 7. Styleguide, Regeln, Wissen

- **Styleguide** (`styleguide.ts`): wird aus Theme-Konfiguration, Storefront-CSS, Logo und Texten abgeleitet (`get_brand_signals` → `save_styleguide`) und im Prompt als verbindlicher Block mitgegeben. Er liefert zusätzlich CSS-Variablen (`--sg-*`) für Vorschau und Custom-HTML. Freitexte darin gelten als Daten, nicht als Anweisung.
- **Regeln** (`knowledge.ts`, Tabelle `rules`): Text, Bereich (`all|products|pages|seo`), optional `target` (Kategorie). Der Prompt-Block ist gedeckelt (40 Regeln, 3000 Zeichen), der Rest über `list_rules`. Kategorie-Regeln stehen mit Name und ID im Block; die KI prüft die Zugehörigkeit über die Kategorien des Produkts.
- **Wissen**: Dokumente werden in Abschnitte zerlegt und lokal per BM25 durchsucht (`search_knowledge`, `get_product_knowledge`). Auszüge sind Daten, keine Anweisungen, und erscheinen mit Quelle. Hochgeladene Inhalte werden vor der Aufnahme mit dem Nutzer bestätigt.

## 8. Shop-Check und eigene Prüfungen

- **Register** (`checks.ts`): `registerCheck`/`registerPlatformCheck` mit `id`, `area`, `scopes`, `platforms`, `run`. `run` liest nur über den geschützten Lese-Client des Durchlaufs und liefert `CheckFinding`s mit `fixPrompt`.
- **Durchlauf** (`shopcheck.ts`, `shopcheck-run.ts`): höchstens ein Lauf gleichzeitig, Parallelität 3, 90 s je Prüfung, Fehler je Prüfung isoliert; Ergebnis im kv-Speicher, gültig für denselben Shop und dieselben Bereiche. Veraltet nach 6 Stunden (unvollständige Läufe nach 5 Minuten). Bereiche, die in den Einstellungen gesperrt sind, werden übersprungen.
- **An/Aus**: `checks_disabled` (Liste von IDs); der Durchlauf filtert sie.
- **Eigene Prüfungen** (`lib/custom-checks.ts`, `server/custom-checks.ts`): deklarativ, Bedingungen über feste Felder (`descriptionWords`, `descriptionChars`, `metaTitleChars`, `metaDescriptionChars`, `nameChars`, `price`, `listPrice`, `stock`, `hasImage`), Vergleiche `lt|lte|gt|gte|eq|neq`, Verknüpfung `all|any`. Kein Code, keine freien Abfragen.
- **Neutrale Produktsicht**: `PlatformAdapter.scanProducts(reader)` liefert aktive Produkte als `NeutralProduct` (Deckel 2500 Produkte, bei Shopify 1000; `capped` → „mindestens“). Shopware: `platform/shopware/scan.ts`; Shopify, Magento, OpenMage: `neutralScan` in ihrer `checks.ts`, aus demselben Scan wie die eingebauten Prüfungen (je Durchlauf einmal gelesen). Unbekannte Werte (`null`) treffen nie zu.
- **Chat-Werkzeuge** (`features/shopcheck.ts`): `list_checks`, `create_check` (mit Probelauf: Trefferzahl vor dem Speichern), `update_check`, `set_check_enabled`, `delete_check`. Anlegen, Ändern, Löschen und Ausschalten fragen den Nutzer.
- **API**: `GET /api/shopcheck`, `POST /api/shopcheck` (neu prüfen), `GET /api/shopcheck/checks`, `PUT|DELETE /api/shopcheck/checks/{id}`.

## 12. Mehrsprachigkeit / Internationalization

Oberfläche und KI-Antworten gibt es auf Deutsch (Standard) und Englisch. Alles liegt in `src/lib/i18n/`:

| Datei | Aufgabe |
|---|---|
| `locales.ts` | `LOCALES` (`'de' \| 'en'`), `DEFAULT_LOCALE = 'de'`, `LOCALE_NAMES`, `INTL_LOCALE` (BCP-47-Tag für `Intl`: Datum, Zahlen), Cookie `LOCALE_COOKIE = 'lotse_lang'`; `resolveLocale` (Cookie vor `Accept-Language` vor Standard) und `requestLocale(req)` für Route-Handler |
| `messages/<ns>.ts` | typisierte Wörterbücher je Namensraum (`common`, `chat`, `settings` …): `export const de = {…}` und `export const en: typeof de = {…}`. Der Typ erzwingt dieselben Schlüssel; Texte mit Platzhaltern oder Plural sind Funktionen (`t.common.minutesAgo(5)`). `tests/lib/i18n.test.ts` prüft, dass beide Sprachen dieselbe Form haben |
| `index.ts` | `messages(locale)` → `Messages`, `formatNumber(n, locale)` |
| `I18nProvider.tsx` | Client-Kontext: `useT()` (Wörterbuch), `useLocale()`, `useI18n()` (mit `setLocale`). Ein Wechsel setzt das Cookie, `<html lang>` und lädt die Server-Teile per `router.refresh()` neu |
| `server.ts` | `getLocale()`/`getMessages()` für Server-Komponenten und `generateMetadata` (Cookie, sonst `Accept-Language`) |

Der Umschalter (`components/i18n/LanguageSwitch.tsx`) steht in den Einstellungen und in der seitlichen Navigation. Es gibt keine Sprach-Präfixe in den URLs; Server und Client rendern mit derselben Sprache aus dem Cookie.

**KI-Antworten.** `POST /api/chat` bestimmt die Sprache mit `requestLocale(req)` und setzt sie als `Session.locale`. `buildSystem(kind, locale)` (`server/prompt.ts`) hängt den passenden `REPLY_LANGUAGE`-Block an: Chat-Antworten, Rückfragen und Begründungen in der Sprache der Oberfläche; Inhalte für den Shop in der Sprache, die der Nutzer bzw. der Shop/Verkaufskanal verlangt. Die Prompts in `prompts/` bleiben bewusst deutsch (interne Anweisungen an das Modell, keine Nutzertexte).

Nicht übersetzt werden Texte, die vom Server oder aus dem Shop kommen (Fehlertexte der API, Ausgaben der KI, Shop-Daten).
